## ② 方法

1. **探针全部自己重写**，不照抄 `qa/probe-coldlt.js` / `qa/probe-coldtimeline.js`。特别避开了「第一次轮询就退出」的坑：两者都要求先看到 `running===true`（`started !== null`）才允许判定结束，我的探针在此基础上把**所有时间戳都放在页面内用 `performance.now()` 取**，避免 CDP 往返把延迟算进去。
2. 计时口径：
   - **墙钟**：页面内 `t0 = performance.now()` → `document.getElementById('gl-tab-cold').click()` → 1 ms `setInterval` 轮询记录 `running` 首次为 `true`、`progress` 首次 `>=0.999`、`running` 首次为 `false`。轮询本身在主线程被长任务饿死，饿死后的下一次回调即"块结束"，误差 ≤ 4 ms。
   - **长任务**：`PerformanceObserver({entryTypes:['longtask']})`，装在 `addInitScript` 里（页面脚本之前）。
   - **TBT（口径）**：Σ max(0, duration − 50)。
   - **收尾块另一种独立量法**：`state.hatchMs` 是页面自己在 `80-coldstart.js:336` 取 `performance.now()`、在 `:417` 相减得到的，直接读出来即可（不改代码）。
   - **交互延迟**：Node 侧记录发车时刻，页面内监听器记录事件到达时刻，用 `performance.timeOrigin/Date.now()` 桥接（±3 ms 级）。`page.click` 额外含 Playwright 可达性检查（属端到端口径，已注明）。
   - **「三态是否真上屏」**：① 逐帧（rAF）读 `#gl-cold-phase.textContent`（rAF 回调与绘制同帧）；② 拦截该元素的 `textContent` setter，原样转发给原生 setter，只记录每次赋的值。二者对照。
3. 规模：**22 次页面会话/运行**（主表 5 次、交互 8 次、状态行 2+2 次、归因 2 次、rAF 对照 3 次）。
4. 产物（都在 `review/ds41/w3c-coldperf/`）：`probe-coldperf.js`、`probe-interact.js`、`probe-textstates.js`、`probe-textstates2.js`、`probe-attrib.js`、`probe-raf.js`、`analyze.js`、`analyze-interact.js`、`raw-*.txt`、`summary-*.txt`。

- 原因：`80-coldstart.js:230-232` 三行同一任务，写完状态行立刻进入 1–2 s 同步块，浏览器没有任务边界可以绘制；块结束时 `:443 st.phase='完成'`、`:446 render()` → `updateProgressUI()` 已经把文本换成"上次计算完成"，**中间值被覆盖，从未合成一帧**。

→ **你这一轮加状态行的设计意图（让用户知道最后 1 秒在干什么）目前没有达成**：用户在收尾块里看到的是冻结的「正在计算：100%…」。

## ④ 对 `finish()` 收尾块的具体优化建议（只提建议，未改代码）

前提事实：收尾块 = `80-coldstart.js:335–418`，其中 **99.9% 是 `:341` 循环里 6 次 `G.pllTrack`（`:358`，单次 181 ms 均值 / 190 ms 峰值）**；`:339/:394/:403-414/:419-442` 合计 ~32 ms。你上一轮"把细块生成分片"之所以 4.53→5.61 s 且最长块不降，是因为**分片切错了地方**——细块生成在 `step()`（`:262-283`）、属于步进阶段，而最长块在 `finish()` 的 `pllTrack`。

### P0-A：把 `finish()` 的载波环循环按「卫星」分片（首选，收益/代价最好）

- 改哪里：`80-coldstart.js:341` 的 `for (k7 = 0; k7 < info.sats0.length; k7++)` 改成"每颗一个任务"的续跑（`setTimeout(...,0)`）；把 `:399-402`、`:403-414`、`:419-446` 收进"最后一片"里执行；`prMAt / smoothAt / pllStats / pass2Count / lockedAll` 提到 `finish()` 外层（闭包/状态对象）保存，避免每片重算。
- 每片加一行 `st.phase='正在做载波环 '+k+'/'+n` + `updateProgressUI()`（见 P0-B）。
- 预期：**最长单块 1527.6 ms（实测中位）→ ≈ 190–200 ms**（= 单颗 `pllTrack` 峰值 190.4 ms + 该颗杂项 <1 ms）；TBT 从 ~3272 ms 降到 ~2600 ms（收尾 1477 ms → 6×~140 ms）。
- 代价：改动约 30–40 行，需要把 `finish()` 后段改成可重入；总时长预计 +5~20 ms（6 次调度）；风险点是闭包变量作用域（漏提会导致数值变化）——**必须跑一次数值回归**（`chipsRms / hatchRms / kfRms / err / pllLocked / pllPass2Count` 应与现在逐位一致）。
- 这一步不会降低 CPU 总量，只是把 1 个 1.5 s 的块换成 6 个 0.19 s 的块 —— 对"看起来卡死"是决定性改善。

### P0-B：让中间态真的能被画一帧（2 行，必须和 A 一起做）

- 改哪里：`80-coldstart.js:230-232`。现在 `st.phase=...`、`updateProgressUI()`、`finish(info)` 在同一任务。把 `:232` 改成 `setTimeout(function(){ finish(info); }, 0);`（或在 `finish()` 开头再加一次 `requestAnimationFrame` 让出）。
- 预期：中间态从"从不出现"变成"至少可见 1 帧"；成本 ~16 ms（1 帧）。
- 这是本次改动**投入最小、收益最直接**的一条：只差一次让出主线程。

### P1-A：降低单颗 `pllTrack` 的绝对成本（把 6×181 ms 变小）

- 根因在 `correlateIQ`（HTML 内 `:1039-1049`）：每个样本 `Math.cos(ph)` + `Math.sin(ph)` + 3 次取模， 200 块 × 16368 样本 × 6 颗 ≈ **1960 万次迭代 / 3900 万次三角函数**。
- 可动的点：① `:1041-1042` 的 `tt`/`chip` 计算与 `j` 无关，可按 `codePhaseSamples` 预先取模一次、块内用增量；② `:1044-1045` 的 `cos/sin` 在 `fNcoHz`、`fs`、`n` 固定时是按 `j` 的线性相位，可用旋转递推或查表（需给量化误差论证）；③ 细块 `fs=4092000`（`80-coldstart.js:275`）对教学目的偏大，降到 1.023 MHz 或 `ms:4→1` 能把样本数降到 1/4。
- 预期（**推断，未实测**）：①+② 有望把单颗 181 ms 降到 60–90 ms → 整个收尾块 1.5 s → 0.4–0.6 s；③ 会改变相干积分/抗噪结果，属"改结论"，必须先做 A/B 数值比对。
- 代价：①+② 要动被多处复用的核心模块（CONTRACT 里判据化的成品），风险高于 A；建议在 A 落地后再评估。

### P2：不要让进度条停在 100% 干等

- 改哪里：`80-coldstart.js:284`（`st.progress = .../st.epochs`）只到 1.0 就结束。建议细块/收尾阶段把进度上限压到 0.95，留 5% 给载波环/Hatch/KF，让进度条在收尾块期间仍有"未完成"的视觉信号（配合 A 的分片可继续增长）。
- 代价：改 1–2 行 + `updateProgressUI()` 里的百分比算法；风险低。

### P2：历元 0 的 6 次捕获（240–380 ms/次，合计 ~1.6 s，占 TBT 另一半）

- 这是 `step()` `:244 acquireOne` 的固有成本，若要继续压 TBT，就得动 `acquireOne` 的搜索网格或降采样。**不属于本次"收尾块"范围**，仅登记为后续候选。

## ⑤ 未验证边界

1. **机器/浏览器差异**：以上数字全部来自本机 headless Chromium（软渲染、每次全新 browser 进程）。你之前实测总时长 ~4.5 s、收尾块 ~1001 ms；我这边中位总时长 **6054.6 ms**、收尾块中位 **1527.6 ms**。**结构完全一致（收尾块 = 一个长任务、由 6 次 pllTrack 主导），但绝对量级偏大约 30–50%**，不能直接与你的 4.5 s/1001 ms 相减或比对。有头模式、带 GPU、非首次（JIT 热了之后）的数字未验证。
2. **首次可交互时间（TTI）**：没有标准 API，我用的代理定义是"从 `navigationStart` 到 DOMContentLoaded 之后首次出现连续 2 个 rAF 间隔 ≤33 ms"，得 90.0–110.4 ms。**这不是规范定义的 TTI**，也未与真实用户可交互事件做过对齐验证。
3. **`running` 首次为 true 的 310 ms** 是"被第一个捕获长任务饿死后的观测值"，不是 `run()` 真实开始时刻；真实开始 ≈75–90 ms 是**推断**（依据 click 事件到达 + `90-boot.js:49-51` 的两帧 rAF 链）。
4. **rAF 间隔口径**：如 3.5 所述不可靠（帧合并 + 切片缺陷），未作为冻结证据；若要 rAF 口径的冻结证据，需要改用"块结束后的第一帧"对齐方式重测。
5. **细粒度归因的边界**：`pllTrack 99.9%` 是在**内存里给它套了一层计时包装**得到的（原样透传、不改文件）。包装自身的开销 ~1 ms（1087.4 累计内），可忽略；但"包装后是否改变 JIT 内联"未验证。`hatchMs`（页面自测）与包装总计一致（1087.4 vs 1086.5），互为印证。
6. **优化预期值**：④ 里"分片后 190–200 ms""TBT → ~2600 ms"是**基于实测单颗成本做的推算**，不是实跑结果；"查表/递推把单颗降到 60–90 ms"是**推断**，未做原型。
7. **交互测试的干扰**：滑杆测试拖的是 `#gl-cold-n`（只影响下一次运行的 `setup()`，已核对 `st.n` 仅用于 `:86`，不进入在飞这次的 `finish()`）；`#gl-tab-ca` 的首次切换会触发 `ca.render()`；wheel 会让页面滚动。这些都未做"无冷启动"对照组，故延迟数字里含少量由交互自身引发的渲染开销。
8. **未测**：真机（非 headless）、移动端/触屏、键盘操作延迟、`prefers-reduced-motion`、把 26 个滑杆逐个测一遍（只测了 1 个滑杆 + 1 个标签 + 滚动）。
9. **未验证**：`firstShow()` 在"几何变化后再首次进入冷启动"（`stale` 路径）时是否有额外耗时；本轮只测了最纯净的首次进入。
